### A. `@recursica/adapter-common` cannot be a real runtime dependency of this adapter — it is a React package

`packages/adapter-common/package.json` declares:

```json
"peerDependencies": { "react": ">=16.8.0", "react-dom": ">=16.8.0" }
```

`RecursicaThemeProvider.tsx` is a React function component (`useEffect`, JSX, `forwardRef`-based `Layer.tsx`). `src/utils/mergeStyles.ts`, `copyToClipboard.ts`, and `overStyledControl.ts` all `import React from "react"` or use React hooks directly; `wrapComponent.tsx` is JSX. `types.ts` itself opens with `import React from "react"` and several exported interfaces (`RecursicaLabelProps`, `RecursicaFormControlWrapperProps`) embed `React.ReactNode`/`React.MouseEventHandler` in their shape.

**Consequence**: `CREATING_AN_ADAPTER.md` step 4/5's instructions to "keep `@recursica/adapter-common` as a real dependency" and have `src/components/index.ts` "re-export everything from `@recursica/adapter-common`" (including `Layer`/`RecursicaThemeProvider`, which step 9 says to exclude from stubbing "since those are already covered via `@recursica/adapter-common`'s re-export") **do not apply to this adapter**. There is no Angular build of `adapter-common`, and importing a React component tree into an Angular template is not a real option (no interop layer exists in this stack; would require something like `ngx-react`-style wrapper bridges Recursica doesn't use anywhere). This directly answers the monorepo's own open question ("whether a given UI kit's adapter actually needs `adapter-common` as a real dependency") for Angular: **no, not as an npm dependency.**

What _is_ portable, evidence-checked file by file:

- **Fully portable, framework-agnostic types** (no React import, pure TS): `RecursicaSpacing`, `RecursicaSize`, `BlockedStylingKeys`, `ForbiddenStyles`, `WithRecursicaSpacing<T>`, `RecursicaOverStyled<T, Allow>`, `RECURSICA_COMPONENTS`/`RecursicaComponent` — these can be hand-copied verbatim into this adapter's own `src/types/index.ts` (not imported from the npm package — the package itself still requires `react`/`react-dom` peers to even install cleanly).
- **Fully portable, framework-agnostic logic** (no React import): `omitUnsupportedProps.ts`, `mergeClassNames.ts`, `withCallerOverride.ts` — pure functions operating on plain objects, no React dependency at all. Same treatment: copy the logic into this adapter's own `src/utils/`, don't import the package.
- **Not portable as-is, needs an Angular-native reimplementation**: `RecursicaThemeProvider` (React component + `useEffect`) and `Layer` (React `forwardRef` component). Both are small and simple enough to port faithfully — see Crosscutting Finding B and Q10 below — but they must be _written_, not imported, for this adapter. This means, uniquely among adapters so far, **`Layer` and `RecursicaThemeProvider` belong at the front of this adapter's build order**, not excluded from it.

### B. Angular Material's own theming is a Sass build-time system, not a runtime JS provider — there is no `useTheme()`/`ThemeProvider` equivalent anywhere in the package

Every prior adapter's underlying kit ships a JS/React runtime theming API (`MantineProvider`, `BeamThemeProvider` + `useBeamTheme()`). Angular Material has **no runtime theming API at all**. Theming is 100% Sass: the consuming app's own `.scss` entry point does `@use '@angular/material' as mat;` then `html { @include mat.theme((color: ..., typography: ..., density: ...)); }` (`node_modules/@angular/material/core/tokens/_system.scss`, the `theme()` mixin, confirmed by reading the mixin body directly). This mixin emits literal `--mat-sys-*` CSS custom properties at whatever CSS selector you call it under — there is no `MatThemeService`, no injectable "current theme" token, no hook. Full implications are in Q1/Q2/Q10 below. This is the single biggest reason Q10 for this adapter looks nothing like the Beam or Mantine answer.

### C. Most Angular Material "components" are attribute directives applied to a real native element, not custom elements — confirmed for Button and Input specifically

`MatButton`'s selector (`node_modules/@angular/material/types/button.d.ts`, `ɵcmp` declaration) is:

```
button[matButton], a[matButton], button[mat-button], button[mat-raised-button],
button[mat-flat-button], button[mat-stroked-button], a[mat-button], a[mat-raised-button],
a[mat-flat-button], a[mat-stroked-button]
```

i.e. `<button matButton>` — a directive-shaped component that decorates a real `<button>`/`<a>`, not `<mat-button>`. Same pattern for `MatInput` (`matInput` directive on a real `<input>`/`<select>`/`<textarea>`, confirmed in `types/input.d.ts`). This is trivial to wrap (Recursica's own `<rec-button>` Angular component's template is just `<button matButton [appearance]="...">`) but worth knowing up front — it means "what underlying element does Recursica's wrapper render" is a real per-component question here in a way it wasn't for Mantine/Beam (both of which always render their own custom element).

### D. Every real form control (`MatInput`, `MatCheckbox`, `MatSelect`, `MatSlideToggle`, `MatRadioButton`, `MatDatepickerInput`, `MatChipGrid`, …) implements Angular's `ControlValueAccessor`/`Validator` and is meant to be driven by `ReactiveFormsModule`'s `FormControl`/`formControlName`, not local component state

Confirmed directly on `MatCheckbox` (`implements ... ControlValueAccessor, Validator`) and `MatInput` (`ngControl: NgControl` injected directly, `_errorStateTracker` reacting to `NgControl`'s validity state) in their respective `.d.ts` files. This is the task brief's warning made concrete: a Recursica field wrapper here isn't "manage `value`/`onChange` in component state," it's "either accept a `FormControl`/`ngModel` from the caller and let Angular's forms machinery own state, or accept a plain value/emit `(valueChange)` and manually implement `ControlValueAccessor` to interoperate with the caller's own reactive form." This is a real, per-component design decision Recursica hasn't had to make for any prior (React) adapter — flagging as a genuinely new API-surface question for `RecursicaOverStyled`-style contracts to answer once real components are built (out of scope for this report, but load-bearing for step 10 item 1's prop audit on every form-shaped component).

## 1. How does the underlying kit prefer to style components?

**Plain CSS, generated at build time from Sass, delivered as a literal string embedded in each component's compiled JS — and, critically, with `ViewEncapsulation.None`, not Angular's default `Emulated`.**

Reading `node_modules/@angular/material/fesm2022/button.mjs` directly (this is Angular's "partial compilation"/Ivy format used for library distribution — real, readable TypeScript-compiled-to-JS with `@Component`-equivalent metadata reconstructed via `ɵɵngDeclareComponent`, not minified):

```js
static ɵcmp = i0.ɵɵngDeclareComponent({
  ...
  template: "<span class=\"mat-mdc-button-persistent-ripple\" ...>...",
  ...
});
```

and the actual CSS, verified present as a plain string in the same file:

```js
styles: [".mat-mdc-button-base {\n  text-decoration: none;\n}\n...
.mat-mdc-button {\n  padding: 0 var(--mat-button-text-horizontal-padding, 12px);\n
  height: var(--mat-button-text-container-height, 40px);\n
  font-family: var(--mat-button-text-label-text-font, var(--mat-sys-label-large-font));\n  ..."],
encapsulation: i0.ViewEncapsulation.None
```

Checked this isn't a Button-specific fluke: **every one of the 41 component bundle files under `fesm2022/*.mjs` that declares an `encapsulation:` key declares `ViewEncapsulation.None`** (`grep -l "ViewEncapsulation.None" fesm2022/*.mjs` → 41 files; `grep -l "ViewEncapsulation.Emulated"` → 0 files). This is a deliberate, consistent Angular Material architecture choice, not an accident:

- Angular's _default_ encapsulation (`ViewEncapsulation.Emulated = 0`, confirmed in `node_modules/@angular/core/types/core.d.ts`'s `declare enum ViewEncapsulation`) adds a per-component `_ngcontent-xxx` attribute to every element and rewrites the component's CSS selectors to include that attribute — genuine Shadow-DOM-_like_ per-instance scoping, done by Angular's compiler.
- Angular Material opts **out** of that for all of its own components (`ViewEncapsulation.None`) and instead relies entirely on **fixed, unhashed, stable class names** (`mat-mdc-button`, `mdc-button`, `mat-mdc-unelevated-button`, `mat-pseudo-checkbox`, …) — the same BEM-ish-but-MDC-flavored convention every build produces identically. Angular still only injects each unique component style string into the document's `<head>` once (deduplicated by content, not per-instance) — practically indistinguishable from "one global stylesheet," just injected by Angular's runtime instead of a `<link>` tag or bundler CSS import.
- Every visual value (color, size, radius, shadow, typography) is one level of indirection through a CSS custom property, almost always with an inline fallback: `color: var(--mat-button-text-label-text-color, var(--mat-sys-primary));`. The `--mat-sys-*` names are Angular Material's Material-3 **system-level** tokens (semantic, theme-driven); the `--mat-button-*`/`--mat-checkbox-*`/etc. names are **component-level** tokens that fall back to the system tokens when unset. Zero hardcoded colors/sizes found in any sampled component stylesheet (Button, Checkbox via `_pseudo-checkbox-chunk.mjs`) — confirms the same "everything is a variable" architecture Beam has, just with Angular Material's own two-tier (system + component) variable naming instead of Beam's single `--bm-comp-*`/`--bm-sem-*` split.

**Does importing a component side-effect-import its styles, or is there a separate step?** Neither React idiom applies literally. There is no `import "@angular/material/button/button.css"` — the CSS _is_ the component's own compiled JS module (the `styles: [...]` array is part of the same file that defines the `MatButton` class). Using `MatButton` in a template — i.e. adding `MatButtonModule`/`MatButton` to a component's `imports` array and writing `<button matButton>` — is what pulls the styles in; Angular's runtime inserts them into `<head>` the first time the component type is instantiated. There is no separate "import the stylesheet" step for a component's own look, matching the _effect_ of Mantine's/Beam's side-effect CSS imports, achieved by a completely different mechanism (compiler + DI-driven style injection, not a bundler).

**Verified from source**: encapsulation value, presence of `styles:` arrays, custom-property-driven values, stable class names — all read directly from `fesm2022/*.mjs`. **Not verified (would need a running app)**: the exact runtime behavior of Angular's style-injection dedup (e.g. whether Angular's newer esbuild-based application builder extracts these into a separate `.css` file at build time rather than injecting via JS at runtime — this is a real, version dependent behavior of Angular's _build tooling_, not `@angular/material` itself, and no Angular CLI project exists yet in this repo to check against). Flagging as a gap for step 5's tooling decisions.

## 2. How are the underlying kit's own styles included?

Two independent things must be wired up, and they are **not both optional** — a component with no `mat.theme()` call anywhere in the app's CSS will render structurally correct HTML with mostly _invisible_ styling, because nearly every component-level variable's fallback chain bottoms out at a `--mat-sys-*` variable that plain installation never defines:

1. **The Sass theme, via `@use '@angular/material' as mat;` + a `mat.theme(...)` (or legacy `mat.all-component-themes($theme)`) call somewhere in the app's global stylesheet.** This is a **required build-time step**, not an import — it needs a Sass compiler in the build pipeline (`sass` npm package; Angular CLI apps get this via `@angular-devkit/build-angular`'s bundled Sass support, but this adapter doesn't have an Angular CLI project yet — see the open item below). Confirmed by reading `node_modules/@angular/material/core/tokens/_system.scss`'s `theme()` mixin: it emits the `--mat-sys-*` variables (`_output_token($prefix, $name, $value)` → `--mat-sys-<name>: <value>;`) that every component's own CSS falls back to. Skip this and buttons/checkboxes/etc. render with no color, no radius, no elevation — visually broken, not just "unthemed."
   - Also confirmed: `core()` (`core/_core.scss`) — the mixin every Material tutorial has historically told you to call once for global resets/structural styles — **is now a documented no-op in this version** (`/// @deprecated This mixin is a no-op and is going to be removed in v21. @mixin core() {}`). Don't port this instruction from any older Material adapter guidance; it does nothing in 22.x.
2. **CDK structural CSS for overlay-based components.** `node_modules/@angular/cdk/overlay-prebuilt.css` (positioning/backdrop for the CDK Overlay service) is required by _any_ component built on it — and that's most of the catalog: Menu, Select, Autocomplete, Dialog, Tooltip, Datepicker, Timepicker, SnackBar, BottomSheet all import `@angular/cdk/overlay` internally (confirmed via `import '@angular/cdk/overlay'`-style imports scattered through their `fesm2022` bundles). `@angular/cdk/text-field-prebuilt.css` (autosizing textarea) and `@angular/cdk/a11y-prebuilt.css` (visually-hidden/live-announcer support classes) are the other two prebuilt CSS files CDK ships (`ls node_modules/@angular/cdk` → `a11y-prebuilt.css`, `overlay-prebuilt.css`, `text-field-prebuilt.css`). These need to be included in the app's global styles alongside the Sass theme output.
3. Legacy alternative, not recommended: `node_modules/@angular/material/prebuilt-themes/*.css` (8 static M2 palettes, e.g. `indigo-pink.css`) are fully-compiled, ready-to-import stylesheets requiring no Sass step at all — but they're the _old_ Material 2 theming system, light-only (no dark-mode story), and don't emit the same `--mat-sys-*` variable surface the modern `mat.theme()` path does. Not worth building this adapter's override strategy around a legacy, non-dark-mode-capable path.

**Where this leaves `SETUP.md`/`USAGE.md`**: these files don't exist yet in this repo (correctly — they're a step-6 deliverable, and this repo is pre-scaffold). This section is the seed for them, per `CREATING_AN_ADAPTER.md`'s own framing, not a claim that they were written now. When step 6 happens, `SETUP.md` needs to document: (a) a Sass-capable build (Angular CLI's default builder qualifies; a hand-rolled esbuild/Vite setup would need `sass`/`sass-loader`-equivalent wiring — open item, see Q3), (b) the app's own `mat.theme()` call, (c) the three CDK prebuilt CSS imports, (d) `recursica_variables_scoped.css` + this adapter's own compiled CSS, in that order, (e) whatever `RecursicaThemeProvider` ends up being for Angular (a component wrapping `<ng-content>`, most likely — see Q10).

**Verified from source**: the `theme()`/`core()` mixin bodies, the CDK prebuilt CSS files' existence and which subpackages reference `@angular/cdk/overlay`. **Not verified**: an actual end-to-end build proving this exact set of imports produces a correctly-themed running page (no Angular CLI project/Storybook exists yet to build). Flagging as a step-7 verification item once real scaffolding exists.

## 3. Can CSS Modules override the underlying kit's styles without touching global/underlying-kit styles?

**Yes for the "override the underlying kit's styles" half — but "CSS Modules" the literal mechanism (hashed-classname `.module.css` imports, as used by mantine-adapter and beam-adapter) is not a concept Angular's own tooling supports at all. This needs a human decision before step 8, not an assumption carried over from the React adapters.**

Two separate things worth separating cleanly:

**(a) Is overriding Material's own styles from outside achievable without touching Material's own selectors/global scope?** Yes, cleanly, for the same structural reason as Beam: Material's own CSS (§1) is entirely custom-property-driven with fallback chains (`var(--mat-button-text-label-text-color, var(--mat-sys-primary))`). Redeclaring `--mat-button-text-label-text-color` on a specific element (or a specific attribute-scoped selector wrapping it) overrides Material's rendered value without ever writing a rule that touches `.mat-mdc-button` or any global selector — same mechanism Beam's `--bm-comp-*` override strategy uses, and it composes fine with `ViewEncapsulation.None`'s "everything is one global stylesheet" model precisely _because_ the override is a variable redeclaration scoped by a normal CSS selector (an attribute or a wrapper class), not a global rule rewrite.

**(b) Is "CSS Modules" (the actual bundler mechanism: `*.module.css` imported as a JS object of locally-hashed class names, e.g. `styles.root` in mantine-adapter/beam-adapter) available in Angular's build tooling at all?** **No — not natively, in either of Angular's two realistic build paths**, and this is a load-bearing gap for step 8, not a minor detail:

- The Angular CLI's own builders (`@angular-devkit/build-angular`'s classic Webpack builder, and the newer default `@angular/build` esbuild-based "application" builder) compile `styleUrls`/inline `styles` on the `@Component` decorator through Angular's own template/style pipeline (Sass/Less preprocessing → Angular's `ViewEncapsulation` scoping). Neither has a documented `*.module.css` → locally-scoped-class-map import convention the way Vite/webpack's `css-loader` `modules: true` option does for a plain TS/JS import. (This is Angular tooling architecture — well-established from prior Angular work, not something installable node_modules content could prove one way or the other without an actual `angular.json`/build attempt, which doesn't exist yet in this repo. Flagging as **inferred with high confidence from known Angular build-tool architecture, not independently re-verified against a scaffolded build in this pass** — a real, cheap thing to confirm the moment step 4 scaffolds a build.)
- Angular's own **native** answer to "scoped styles per component" is `ViewEncapsulation.Emulated` (the default for any component that doesn't opt out) — Angular's compiler rewrites the component's own CSS selectors to include a generated `_ngcontent-<hash>` attribute and stamps the same attribute onto every element the component's template renders, and the _host_ element gets a paired `_nghost-<hash>` attribute. This achieves the same practical goal CSS Modules exists for (a consumer can't casually guess/target Recursica's own internal class names — see Q3 of `docs/STYLING_SYSTEM.md`'s framing in the Beam report) — but via **attribute selectors generated by the Angular compiler at build time**, not **hashed class names generated by a bundler loader at import time**. The two are not interchangeable line-for-line: there's no `styles.root`-shaped JS object to reference in a template the way `className={styles.root}` works in JSX; instead, a plain unprefixed class like `.root` written directly in the component's own `styles.css`/inline `styles` array is _automatically_ scoped by Angular's compiler (as long as `ViewEncapsulation.Emulated` is in effect, which it is by default), and `class="root"` in the component's own template just works, scoped, with zero extra tooling.

**Recommendation for step 8 to actually decide (not decided here)**: adopt Angular's native `ViewEncapsulation.Emulated` (the default — i.e., _don't_ set `ViewEncapsulation.None` the way Material does for its own components) as this adapter's own scoping mechanism, since it's the framework-idiomatic, zero-extra-tooling equivalent of "CSS Modules' hashed classes, but framework-native." This satisfies `docs/CREATING_AN_ADAPTER.md` step 8 point 3's actual requirement (non-guessable, per-build-unique scoping a consumer's stylesheet can't casually target) via a different, Angular-native mechanism — `_ngcontent-<hash>` attributes are just as non-guessable/build-specific as a CSS Modules hash suffix, arguably more so since the hash isn't even present in the authored source, only injected by the compiler. This is a genuine "don't force-fit the mantine/beam structure" case the task brief anticipated — the _goal_ (scoped, non-targetable overrides) holds; the _named mechanism_ ("CSS Modules") literally doesn't exist in this ecosystem and shouldn't be cargo-culted into `STYLING_SYSTEM.md` step 8 as if it will.

**Verified from source**: Material's own `ViewEncapsulation.None` choice and variable-driven CSS (directly read). **Inferred, not independently re-verified in a real build**: that Angular's CLI/esbuild builder has no CSS-Modules-equivalent import convention. **Needs a live check**: actually scaffolding a minimal Angular library/app build and confirming (1) no CSS-Modules-shaped import works out of the box, (2) `ViewEncapsulation.Emulated` really does produce the described attribute-scoping in a real compiled component, before `STYLING_SYSTEM.md` finalizes this as the decision.

## 4. Can appearance-affecting styling props be filtered out — which ones, and is there a generic escape hatch?

**Angular Material components have no generic `sx`/`css`/`classes`/`classNames`-style escape hatch at all — but the _reason_ is architectural, not "the kit chose not to have one": Angular doesn't have component-level "style props" as a concept the way React does.**

In React, `className`/`style`/`sx`/`classNames` are ordinary props threaded through JS objects — a UI kit chooses whether to expose a richer version. In Angular, `[class]`/`[ngClass]`/`[style]`/`[ngStyle]` are **framework-level template bindings that work on any element or component host**, independent of whatever `@Input()`s the component itself declares — a caller can always write `<button matButton [ngClass]="..." [ngStyle]="...">` regardless of whether `MatButton` "supports" it, because it's Angular's own template syntax operating on the host element, not a prop `MatButton` receives and interprets. This means the generic "styling escape hatch" for _any_ Angular Material component is really "Angular's own attribute/class/style host bindings," and blocking it isn't a matter of typing an `Omit<>` on a component's declared props (Recursica's Angular wrapper component's own template controls whether/how a caller's `[ngClass]`/`[style]` even reaches the underlying `matButton`-decorated element in the first place, since the caller is binding onto _Recursica's_ component selector, not Material's directly). This needs its own design pass at implementation time (step 10 for each component) — conceptually equivalent to `filterStylingProps`'s job, but the mechanism has to be host-binding-aware rather than prop-object-aware. Flagging as a real, non-obvious architecture question for whoever designs this adapter's own `filterStylingProps.ts`, not something this report resolves.

**Confirmed appearance-affecting `@Input()`s that _do_ exist per-component** (read directly off each component's `ɵcmp`/`ɵdir` declaration in its `.d.ts`), giving a first-pass sense of the surface to filter, same spirit as the report's job for Beam:

- `MatButton`/`MatIconButton`/`MatFabButton`: `appearance` (`'text'|'filled'|'elevated'|'outlined'|'tonal'`), `color` (`ThemePalette` = `'primary'|'accent'|'warn'`, **documented in the `.d.ts` itself as "supported in M2 themes only, it has no effect in M3 themes"** — i.e. under the modern `mat.theme()` path this adapter should use, setting `color` on a button already silently does nothing; still needs to be in `UNSUPPORTED_PROPS`/`Omit<>` defensively, not trusted to be inert forever).
- `MatCheckbox`/`MatRadioButton`/`MatSlideToggle`: `color`, `disableRipple`, `labelPosition` (`'before'|'after'`).
- `MatCard`: `appearance` (`'outlined'|'raised'` etc.).
- `MatStepper`: `color`, `labelPosition`, `headerPosition`.
- None of the sampled components exposed anything resembling Mantine's large atomic style-prop system (`p`/`bg`/`c`/`fz`/…) or Beam's `m`/`mx`/`gap` layout-prop convention — Material has no margin/padding/gap props on any component at all; **spacing is entirely the caller's own CSS responsibility** (no `LAYOUT_PROPS`-equivalent surface exists on the underlying kit to pass through — this adapter's own `Flex`/`Stack`/`Group`/`Grid`, once built, become the _only_ place `rec-*` spacing tokens have anywhere to attach, more so than for Mantine/Beam where the individual components also accepted some spacing props natively).

**Verified from source**: every `@Input()` cited above, from real `.d.ts` `ɵcmp`/`ɵdir` declarations. **Not yet done** (correctly deferred to step 10 per the guide): the full per-component prop-by-prop audit — this is a first-pass survey only, as instructed.

## 5. Do the underlying kit's own primitives map to Recursica's layout components (`Flex`, `Stack`, `Group`, `Grid`)?

**No — confirmed absent from both `@angular/material` and `@angular/cdk`, same conclusion as Beam, verified independently for this kit rather than assumed.**

- `@angular/material`: no export anywhere resembling a generic flex/grid layout wrapper. `MatGridList`/`MatGridTile` (`node_modules/@angular/material/types/grid-list.d.ts`) is a **fixed-row-height image/tile masonry layout** (Material's "grid list" widget, historically for photo grids) — a specific, different widget, not a general-purpose CSS Grid layout primitive; using it for Recursica's `Grid` would be a false-friend name match, not a real mapping. `MatToolbar`/`MatSidenav`/`MatCard` compose their own internal layout but expose no reusable general layout primitive.
- `@angular/cdk`: the task brief specifically asked to check `@angular/cdk/layout` on its own merits before assuming nothing exists there. Checked directly (`node_modules/@angular/cdk/fesm2022/layout.mjs` and `types/layout.d.ts`): it exports exactly `BreakpointObserver`, `MediaMatcher`, and a `Breakpoints` constants map (predefined media-query strings) via a tiny `LayoutModule`. This is a **responsive breakpoint-detection service** (subscribe to a `BreakpointObserver.observe(query)` Observable to react to viewport size in TS/JS) — genuinely useful for _building_ a responsive `Grid`'s breakpoint logic later, but it is not itself a flex/grid container component and provides zero markup/CSS. Confirmed via direct read, not assumed from the package name.
- No other CDK subpackage (`@angular/cdk/scrolling`, `/portal`, `/overlay`, etc.) offers a layout-container primitive either.

**Conclusion**: `Flex`, `Stack`, `Group`, `Grid` are all **DOES NOT EXIST** — same as Beam's finding, for the same reason (neither kit ships one), and need to be built the same way Beam's were: light wrappers around plain CSS flexbox/grid, as real Angular components (not Material wrappers, since there's nothing to wrap). `@angular/cdk/layout`'s `BreakpointObserver` is worth using internally if `Grid` grows responsive breakpoint props, but it's a building block, not a component to compose from directly.

## 6. Does the underlying kit have generic typography primitives (`Text`/`Title`)?

**No standalone Angular component or directive — Material's typography system is Sass-mixin-only, meant to be `@include`d into an app's _own_ CSS classes, not consumed as a runtime component.**

`node_modules/@angular/material/core/theming/_typography.scss` defines mixins like `body-small`, `body-medium`, `title-large`, `headline-small`, `label-medium`, etc. — each one, when `@include`d inside a Sass selector, emits `font`/`letter-spacing` properties reading from the same `--mat-sys-*` typography variables `mat.theme()` populates. There is no `<mat-text>` element, no `matText`/`matTypography` directive, nothing importable at the TypeScript/component level — this is 100% a build-time Sass authoring convenience for an app's _own_ stylesheets, not a UI-kit component Recursica could wrap the way mantine-adapter wraps Mantine's real `<Text>`/`<Title>` components. (Material _does_ ship CSS utility classes like `.mat-headline-large` generated by a separate `mat.typography-hierarchy()` mixin for consumers who want ready-made classes rather than authoring their own — still not a component with a `variant`/`order` prop.)

**Conclusion**: functionally the same outcome as Beam-adapter's `Text`/`Title` (no Beam CSS-variable surface to hook, so the real visual result came entirely from Recursica's own typography token classes) — except here there isn't even a component shell to wrap; **`Text`/`Heading` need to be built as genuinely new Angular components from scratch** (`<rec-text [variant]>`/`<rec-heading [order]>` rendering a native `<p>`/`<span>`/`<h1>`–`<h6>` with Recursica's own `recursica_brand_typography_*` classes applied directly), same end-state as mantine-adapter/beam-adapter reached, reached by a shorter path here since there's no underlying component API surface to reconcile against at all.

## 7. How does the underlying kit structure form controls?

**Split cleanly into two very different patterns, more so than Beam's "inconsistent but present per-component" finding — confirmed via `.d.ts` for the two representative cases (a generic wrapper for text-like controls, vs. bare content-projected label for choice controls), not assumed to generalize from one example.**

**Pattern 1 — `<mat-form-field>`, for text-like/selectable controls** (`MatInput`, `MatSelect`, `MatAutocomplete` via `MatInput`, `MatDatepickerInput`, `MatChipGrid`): a real, generic wrapper component (`node_modules/@angular/material/types/_form-field-chunk.d.ts`, class `MatFormField`) that any control implementing the `MatFormFieldControl<T>` abstract contract can plug into via content projection:

```html
<mat-form-field appearance="outline" subscriptSizing="dynamic">
  <mat-label>Name</mat-label>
  <input matInput [formControl]="nameControl" />
  <mat-hint>Helper text</mat-hint>
  <mat-error>Required</mat-error>
</mat-form-field>
```

`appearance` (`'fill'|'outline'`), `floatLabel` (`'always'|'auto'|'never'` — whether the label sits inside the field until focus/value, like a placeholder-that-becomes-a-label, not a stacked/side-by-side layout switch), `subscriptSizing` (`'fixed'|'dynamic'` — whether space below the field is always reserved for hint/error text or grows on demand), and content-projected `<mat-label>`/`<mat-hint>`/`<mat-error>`/`[matPrefix]`/`[matSuffix]` slots are all real and confirmed directly off `MatFormField`'s `ɵcmp` declaration (`inputs`, and the seven-element content-projection selector list ending in `"mat-error, [matError]", "mat-hint:not([align='end'])", "mat-hint[align='end']"`). The `MatFormFieldControl<T>` abstract class (`_form-field-control-chunk.d.ts`) that a control must implement to plug in exposes `stateChanges` (an Observable the form field subscribes to for change detection), `ngControl` (direct `NgControl`/`AbstractControlDirective` access — the Angular Forms tie again), `focused`/`empty`/`required`/`disabled`/`errorState`, and `setDescribedByIds`/`onContainerClick`.

**Pattern 2 — bare content-projected label, no description/error slot at all** (`MatCheckbox`, `MatRadioButton`, `MatSlideToggle`): confirmed on `MatCheckbox`'s `ɵcmp` declaration (`types/checkbox.d.ts`) — the `inputs` map has `id`/`required`/`labelPosition`/`name`/`value`/`disableRipple`/`tabIndex`/`color`/`checked`/`disabled`/`indeterminate` and a battery of `aria-*` inputs, but **no `label`, no `description`, no `helperText`, no `error` input anywhere**. The label is the component's own **projected content** (`ngProjectAs: "*"`, i.e. `<mat-checkbox>Accept terms</mat-checkbox>` — whatever's between the tags becomes the label, positioned per `labelPosition`). There is no built-in way to attach a description or error state to a bare `<mat-checkbox>`/`<mat-radio-button>`/`<mat-slide-toggle>` at all — same gap shape Beam had (`Checkbox.d.ts`/`RadioButton.d.ts`/`Switch.d.ts` all lacked a `description`/`helperText` slot), independently confirmed here for Material.

**Layout (stacked vs. side-by-side)**: `MatFormField`'s DOM structure is inherently **stacked only** — the Material Design text-field convention floats the label _above/inside_ the input box and renders hint/error _below_ it; there is no `MatFormField` option, input, or documented pattern for placing the label to the left of the control (side-by-side). Confirmed by reading the full `inputs` list off `MatFormField`'s `ɵcmp` (`hideRequiredMarker`, `color`, `floatLabel`, `appearance`, `subscriptSizing`, `hintLabel`) — nothing resembling a horizontal/label-width/label-position axis exists.

## 8. Given (7): can the underlying kit's form controls be styled to match Recursica's stacked/side-by-side layouts directly, or does this adapter need its own `FormControlWrapper`/`FormControlLayout`?

**Build it — required, for two independent reasons, neither of which `MatFormField` alone solves despite being more capable out of the box than Beam had:**

1. **Side-by-side is architecturally unavailable from `MatFormField` at all** (Q7) — it would need to be faked by placing the label _outside_ `<mat-form-field>` entirely in a caller-built flex row, which then loses `MatFormField`'s automatic `<label for>`/`aria-describedby` wiring to the control (that wiring is internal to `MatFormField`'s own template, keyed to its own projected `<mat-label>`). A `FormControlWrapper` that owns layout (stacked vs. side-by-side) and manually wires `aria-describedby`/`id` association itself — the same responsibility mantine-adapter's own `FormControlWrapper` already takes on — is the only way to get a consistent side-by-side option across _every_ control type, text-like or choice-like.
2. **`MatFormField` only covers text-like controls, not choice controls at all.** `MatCheckbox`/`MatRadioButton`/`MatSlideToggle` are not `MatFormFieldControl`s and are never placed inside `<mat-form-field>` in Material's own design (confirmed: none of their `.d.ts` files reference `MatFormFieldControl`, unlike `MatInput`/`MatSelect`/date/time inputs, which explicitly `implements MatFormFieldControl<any>`). So even a purely-stacked adapter still needs a _second_, hand-built label+description+error layout for choice controls, since `MatFormField` structurally cannot wrap them. This is the same "richer field components solve it, bare choice controls don't" split Beam had (`InputChoiceGroup` vs. bare `Checkbox`/`RadioButton`/`Switch`), independently reached here for a different underlying reason (Material's form-field contract is type-scoped, not "some components happen to lack a prop").

**Recommendation, not yet built, for whoever picks this up**: `FormControlWrapper`/`FormControlLayout` should be built as genuinely new Angular components (mirroring mantine-adapter's own architecture, which _also_ needed this despite Mantine having a native `description` prop on its inputs — Recursica's own `formLayout: "stacked"|"side-by-side"` concept has never existed natively in any UI kit surveyed so far). For text-like controls, it's reasonable to keep using `<mat-form-field>` internally for the _stacked_ case (it already does label/hint/error positioning correctly there) and only bypass it for the _side-by-side_ case; for choice controls, bypass `MatFormField` entirely in both layouts and hand-build label/description/error the same way for both, matching the "bypass-and-hand-build" precedent both mantine-adapter and beam-adapter already reached for their own kits' gaps. This is a recommendation for step 8/10 to make deliberately with a human, not a decision this report is authorized to finalize.

## 10. How does the underlying kit handle light/dark mode, and how does that interact with `RecursicaThemeProvider`?

**This is the biggest architectural departure from every prior adapter: Angular Material has no runtime light/dark API at all. Theming, including light/dark, is entirely a Sass build-time decision the consuming app makes when it calls `mat.theme()`. There is no `useTheme()`/`useBeamTheme()`/`MantineProvider colorScheme` equivalent anywhere in the package — confirmed by reading the actual theming mixin, not by failing to find docs for one.**

Reading `node_modules/@angular/material/core/tokens/_system.scss`'s `theme()` mixin and its helper `_generate-sys-colors($palettes, $type)` directly:

```scss
@function _generate-sys-colors($palettes, $type) {
  $light-sys-colors: m3.md-sys-color-values-light($palettes);
  @if ($type == light) {
    @return $light-sys-colors;
  }
  $dark-sys-colors: m3.md-sys-color-values-dark($palettes);
  @if ($type == dark) {
    @return $dark-sys-colors;
  }
  @if ($type == color-scheme) {
    $light-dark-sys-colors: ();
    @each $name, $light-value in $light-sys-colors {
      $dark-value: map.get($dark-sys-colors, $name);
      $light-dark-sys-colors: map.set(
        $light-dark-sys-colors,
        $name,
        light-dark($light-value, $dark-value)
      );
    }
    @return $light-dark-sys-colors;
  }
  @error 'Unknown theme-type provided: #{$type}';
}
```

and `theme()`'s own default: if the caller's `mat.theme()` color config doesn't specify a `theme-type`, it defaults to `color-scheme` (`@if (not $is-palette and not map.has-key($color, theme-type)) { $color: map.set($color, theme-type, color-scheme); }`). This means **the out-of-the-box, default behavior of calling `mat.theme(...)` once emits every `--mat-sys-*` color variable as a literal CSS `light-dark(<light-value>, <dark-value>)` function call**, not a single static value. `light-dark()` is a real, standard CSS function (baseline-supported in current Chrome/Firefox/Safari) whose resolved value depends entirely on the **used value of the `color-scheme` CSS property** on that element or an ancestor — which in turn defaults to following the OS/browser `prefers-color-scheme` setting unless something explicitly sets `color-scheme: light` or `color-scheme: dark` (forcing one, overriding the OS preference) on a relevant element.

**This gives two architecturally distinct ways to get light/dark switching, and they are not equivalent**:

- **Path A — one `mat.theme()` call, `color-scheme` theme-type (the default), toggle via the CSS `color-scheme` property.** Set `document.documentElement.style.colorScheme = "dark"` (or `"light"`, or remove it to fall back to OS preference) to switch — a pure DOM/CSS operation, zero Sass recompilation, zero JS theme object. This is elegant but means Material's dark mode is driven by a _different_ mechanism/attribute (`color-scheme` property) than `RecursicaThemeProvider`'s own (`data-recursica-theme="light"|"dark"` attribute) unless something explicitly bridges them.
- **Path B — call `mat.theme()` twice, each with an explicit `theme-type: light`/`theme-type: dark`, each scoped under a different selector**, e.g.:
  ```scss
  html[data-recursica-theme="light"] {
    @include mat.theme(
      (
        color: (
          theme-type: light,
          ...,
        ),
      )
    );
  }
  html[data-recursica-theme="dark"] {
    @include mat.theme(
      (
        color: (
          theme-type: dark,
          ...,
        ),
      )
    );
  }
  ```
  This is possible because `_output_token`/`system-level-colors` emit variables under `sass-utils.current-selector-or-root` — i.e. **whatever selector you call the mixin under is where the variables land**, confirmed directly in `_system.scss`. Since Recursica's own `RecursicaThemeProvider` already sets `data-recursica-theme` on `document.documentElement` (confirmed in the real React source, `RecursicaThemeProvider.tsx`: `document.documentElement.setAttribute("data-recursica-theme", theme)`, reactively, on every `theme` prop change via a `useEffect` keyed on `[theme]`), **an Angular port of `RecursicaThemeProvider` that does the exact same thing (set the same attribute on `document.documentElement`) would drive Angular Material's own theme in perfect lockstep, for free, with _zero_ runtime JS bridge needed** — unlike Beam, which needed a hand-written `BeamDarkModeSync` component because `BeamThemeProvider`'s `defaultTheme` prop is mount-only and only `useBeamTheme().setMode()` (a JS API call) can change it after mount. Angular Material has no such trap to fall into, _because it has no runtime API to call in the first place_ — the only lever is the CSS selector the Sass was compiled under, and if that selector is the same attribute Recursica already toggles, one DOM attribute write drives both systems simultaneously, by construction.

**This is the recommendation this report surfaces for whoever writes this adapter's own `RecursicaThemeProvider`/`STYLING_SYSTEM.md`: prefer Path B (`theme-type: light`/`dark` under `[data-recursica-theme="..."]` selectors) over Path A (`color-scheme` + `light-dark()`), specifically because it lets a single, already-necessary Angular port of `RecursicaThemeProvider` (Crosscutting Finding A) be the _only_ thing anything needs to call, with no separate sync step — a materially simpler story than every prior adapter needed.** This is a real, well-evidenced architectural insight from reading the Sass source, not a guess.

**What is honestly NOT verified, and must be checked live before this is trusted**, per the task's explicit standard (a provider's "default"-named prop is a common trap; verify a live toggle, don't just read the type signature):

- **No running app or Storybook exists yet** in this repo (no `angular.json`, no scaffolded components) to actually build the two `[data-recursica-theme="..."]`-scoped `mat.theme()` blocks above and click a real toggle to confirm both Recursica's own CSS (via `recursica_variables_scoped.css`, which presumably has its own `[data-recursica-theme="light"|"dark"]`-scoped blocks, not directly inspected in this pass) and Angular Material's `--mat-sys-*` variables actually flip together on the same attribute write, with no residual stale styling from whichever mode was active first (Angular's per-content-deduplicated style injection, Finding §1, means both light and dark selector blocks' CSS text are present in the document simultaneously at all times — correct behavior _should_ just be "whichever selector matches wins," but this is inferred from CSS cascade rules, not watched happen in a browser).
- Path A's `light-dark()` + `color-scheme` mechanism is asserted to be standards-compliant/broadly supported based on general current web-platform knowledge, not verified against this project's actual browser-support target or tested in any runtime here.
- Whether Angular's esbuild-based build pipeline (once one exists) correctly compiles/orders two `mat.theme()` calls under two different selectors without deduplication surprises (Sass compiles this fine in isolation — not independently compiled and inspected as output CSS in this pass, only read as Sass _source_).
- Whether any _other_ Recursica adapter-common concern that `RecursicaThemeProvider`'s React version also handles (`injectOverStyledStyles()`, `registerOverStyledConsoleCommand()` — both called unconditionally in the real `RecursicaThemeProvider.tsx`, tied to the `overStyled` escape-hatch mechanism from Q4) has an Angular-appropriate equivalent; not investigated in this pass, flagged as a follow-up once `filterStylingProps.ts`'s Angular design is decided.

**Confidence summary for this question**: high confidence on _how Material's own Sass theming mechanism works_ (read directly, mixin logic is unambiguous) and _why Path B is architecturally preferable_ (follows directly from the confirmed mixin behavior plus the confirmed, already-necessary `RecursicaThemeProvider` port). Low/no confidence — explicitly flagged as needing a live Playwright-style check once Storybook exists — on whether this actually renders correctly end-to-end in a browser, which is exactly the kind of claim the task brief says not to assert from types/docs alone.
