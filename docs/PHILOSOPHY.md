# Recursica Angular Material Adapter: Core Philosophy

Recursica's component architecture isn't just a wrapper; it's a strict enforcing layer over Angular Material's API surface. Our primary goal is to ensure consistency, eliminate "design system rot," and provide clear boundaries for application developers using the UI Kit — the same goal every Recursica adapter shares. This adapter reaches it through mechanisms that are genuinely different from every prior (React-based) adapter, because Angular itself works differently from React: there is no props object to strip keys from, no CSS-in-JS or CSS Modules to reach for, and no runtime theming provider on the underlying kit's side at all.

This document serves as the governing framework for why `adapter-angular-material`'s components are built the way they are.

## 1. Strict Separation of Props (The Unified Recursica Prop Layer)

Recursica has a **single universal API surface** internally, regardless of which underlying UI kit backs a given adapter.

- We decouple our visual properties from Angular Material's own: instead of mapping perfectly to Material's `appearance`/`color` inputs, we intentionally use Recursica's own semantic and behavioral structures.
- We intentionally never declare an `@Input()` for an Angular Material prop that collides with or circumvents Recursica's tokens. `MatButton`'s `color` input is a concrete example: Angular Material's own `.d.ts` documents it as having no effect under Material 3 theming, but this adapter still never exposes it — a defensive decision, not a redundant one, since a component whose no-op behavior is undocumented tomorrow shouldn't suddenly leak through.
- **This is structurally simpler here than in a React adapter, and worth understanding why.** A React component can receive an arbitrary props object via JSX spreading (`{...rest}`), so a React-based adapter needs a runtime step (`filterStylingProps`/`omitUnsupportedProps`) to actively delete blocked keys before they reach the underlying component — reading the code isn't enough to prove a prop is blocked; you have to prove the deletion actually executes. Angular components don't spread unknown caller values onto their rendered output at all. A caller can only ever set the `@Input()`s a component actually declares with the `@Input()` decorator — so simply _not declaring_ an input for a blocked Angular Material prop is a complete, compiler-enforced block, with nothing further to verify at runtime for that specific vector.

## 2. Component Wrappers (Leaving Angular Material Alone)

We actively avoid mutating or patching Angular Material's own source, and we never try to out-specify its CSS by rewriting its selectors.

- Angular Material renders its own components with `ViewEncapsulation.None` and reads nearly every visual value — color, size, radius, shadow, typography — through a two-tier custom-property system: component-level variables (`--mat-button-*`, `--mat-checkbox-*`, …) that fall back to system-level semantic variables (`--mat-sys-*`) when unset. Recursica's own overrides redeclare those same variables, scoped to this adapter's own component root, rather than writing a rule against Material's own `.mat-mdc-*` classes and hoping to win the specificity contest. See [`STYLING_SYSTEM.md`](STYLING_SYSTEM.md) §4 for the concrete mechanism.
- Recursica's own additions are scoped with Angular's native `ViewEncapsulation.Emulated` — the framework default, and the framework-idiomatic equivalent of what CSS Modules gives a React-based adapter: a per-build, non-guessable `_ngcontent-<hash>` attribute the Angular compiler stamps onto every selector and every element the component renders, with zero extra build tooling to configure. There is no CSS-Modules-shaped `*.module.css` import convention anywhere in Angular's own build tooling to reach for instead — this genuinely isn't a choice between two available mechanisms, it's the only framework-native one that exists. See `STYLING_SYSTEM.md` §3.
- Many Angular Material "components" are really attribute directives applied to a real native element — `<button matButton>`, not a distinct `<mat-button>` custom element the way Mantine's or Beam's components always render their own element. A Recursica wrapper here (e.g. `<rec-button>`) renders that real, Material-decorated native element internally; a consumer of this adapter never touches Material's own selector directly, and never needs to know Material's components aren't always custom elements at all.

## 3. The `overStyled` Property — the philosophy carries forward; the mechanism is still an open question

Every other Recursica adapter blocks arbitrary styling vectors by default and offers a single, explicit, auditable escape hatch: `overStyled={true}`. **The philosophy is identical here**: by default, a Recursica component should not be trivially overridable from outside, and any deliberate exception to that should be a loud, greppable signal in the codebase — not a quiet, easily-missed one.

**What's genuinely different in Angular, and honestly still unresolved as of this writing**: React's `className`/`style` are ordinary props a component chooses to accept, inspect, and strip from a plain object at runtime. Angular's `[ngClass]`/`[style]`/`[class]` are **template-level host bindings** that work on _any_ element or component host, entirely independent of what `@Input()`s that component declares — a caller can always write `<rec-button [style.background]="'red'">`, whether or not `RecButtonComponent` was ever designed to "support" it, because it's Angular's own template syntax operating on the host element, not a prop the component receives and can choose to discard. Blocking (or deliberately permitting) that isn't a matter of typing an `Omit<>` on a props interface the way `RecursicaOverStyled<T>` does for a React adapter; it depends on how each component's own template is structured — specifically, whether and how a binding on the Recursica host element propagates to the real Angular Material element rendered inside it.

This is left open on purpose rather than papered over with an invented answer. It needs a real design pass at component-implementation time, starting with whichever real component first genuinely needs it — see [`STYLING_SYSTEM.md`](STYLING_SYSTEM.md) §6 and [`../OVERSTYLING.md`](../OVERSTYLING.md) for the current, honest status.

## 4. Expectations for External Developers (Modifying Recursica)

If a developer finds that a component does not fit their needs and styling must be modified, their path of execution should follow these principles sequentially:

1. **Leverage native Angular Material first.** If a Recursica component lacks the functionality or variant needed for a genuinely custom, one-off case (e.g. a marketing hero button with an arbitrary height), do not try to forcibly hack the Recursica component. Instead, import `@angular/material`'s own directive or component directly (e.g. `MatButtonModule`'s `matButton`) and style it manually. Use Recursica for standard, systematic needs, and Angular Material's own primitives for isolated custom one-offs.
2. **Contribute to the kit, don't build private wrappers.** If the system is genuinely missing a variant, that's a shared project deficit — raise it and have it integrated directly into the component/token set, rather than maintaining a parallel, private wrapper around a Recursica component.
3. **Forms are Angular's own concern, and Recursica's wrappers follow that convention rather than reinventing it.** Most real Angular Material form controls (`MatInput`, `MatCheckbox`, `MatSelect`, `MatSlideToggle`, `MatRadioButton`, `MatDatepickerInput`, …) implement `ControlValueAccessor`/`Validator` and are meant to be driven by `ReactiveFormsModule`'s `FormControl`/`formControlName`, not local component state. This is a genuinely new design axis relative to every prior (React, local-state-driven) adapter: a Recursica field wrapper here either accepts a caller-supplied `FormControl`/`ngModel` and lets Angular's own forms machinery own state, or implements `ControlValueAccessor` itself to interoperate with a caller's reactive form — it does not manage `value`/`onChange` in isolated component state the way a React wrapper naturally would.
